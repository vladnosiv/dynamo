`python -m dynamo.replay` runs one workload through one simulated Dynamo configuration and emits an
AIPerf-style report. This page is the flag and schema reference. For the workflow — input formats,
run modes, and when to use DynoSim versus AIPerf — see [DynoSim Runs](../../cli/operations/simulation-with-dynosim/dynosim-replay.mdx); for
searching many configurations, see [DynoSim Sweeps](../../cli/operations/simulation-with-dynosim/dynosim-sweeps.mdx).

The command reuses the mocker engine, so engine behavior is configured through JSON passed to
`--extra-engine-args` (or the staged `--prefill-engine-args` / `--decode-engine-args`) rather than
individual flags. For the underlying engine settings, see the
[Mocker CLI Reference](mocker-cli-reference.mdx).

`python -m dynamo.replay` requires exactly one of: positional trace files, or all of
`--input-tokens`, `--output-tokens`, and `--request-count`. The `dynamo` format accepts one or more
trace shards. Every other trace format requires exactly one file.

## Workload input

<ParamField path="trace_files" type="positional path(s)" default="null">
  Input trace path. The `dynamo` format accepts one or more JSONL or JSONL.GZ shards. Other formats
  accept one JSONL file. Mutually exclusive with the synthetic-workload flags below.
</ParamField>

<ParamField path="--input-tokens" type="integer" default="null">
  Synthetic per-request input length. Required (with `--output-tokens` and `--request-count`) when no
  trace file is given.
</ParamField>

<ParamField path="--output-tokens" type="integer" default="null">
  Synthetic per-request output length.
</ParamField>

<ParamField path="--request-count" type="integer" default="null">
  Number of synthetic requests. When `--turns-per-session > 1`, this is interpreted as the number of
  sessions, and total completed requests become `request_count * turns_per_session`.
</ParamField>

<ParamField path="--trace-format" type="string" default="mooncake">
  Trace parser.

  <span className="enum-values"><span className="enum-label">Allowed values:</span> <Badge intent="note" minimal>mooncake</Badge> <Badge intent="note" minimal>mooncake-delta</Badge> <Badge intent="note" minimal>agentic_mooncake</Badge> <Badge intent="note" minimal>applied_compute_agentic</Badge> <Badge intent="note" minimal>dynamo</Badge></span>
</ParamField>

<ParamField path="--trace-block-size" type="integer" default="512">
  How many tokens each `hash_id` in the dataset represents. Trace-file runs only; separate from the
  engine `block_size`. Public Mooncake/toolagent traces use `512`. Dynamo request traces embed this
  value; replay derives it when the flag is omitted and rejects an explicit mismatch.
</ParamField>

<Note>
The `mooncake-delta`, `agentic_mooncake`, and `dynamo` formats were added after Dynamo v1.2.1.
The `ai-dynamo` 1.2.x wheels on PyPI accept only `mooncake` and
`applied_compute_agentic`.
</Note>

Apply only to synthetic (non-trace) runs.

<ParamField path="--arrival-interval-ms" type="float" default="null">

</ParamField>

<ParamField path="--turns-per-session" type="integer" default="1">
  Number of turns in each synthetic session.
</ParamField>

<ParamField path="--shared-prefix-ratio" type="float" default="0.0">

</ParamField>

## Trace file schema

Mooncake-style JSONL traces contain one request per line. A basic row accepts:

| Field | Description |
|---|---|
| `timestamp` or `created_time` | Request arrival time |
| `input_length` or `input_tokens` | Input token count |
| `output_length` or `output_tokens` | Output token count |
| `hash_ids` | Prefix-block identifiers from the source trace |
| `priority` | Optional signed soft-priority hint |
| `strict_priority` | Optional unsigned queue tier; larger values run first |
| `policy_class` | Optional requested policy family or exact explicit class |

Example:

```json
{"timestamp": 0, "input_length": 6755, "output_length": 500, "hash_ids": [0, 1, 2, 3]}
```

Rows without `session_id` are independent requests. Priority fields affect only pending requests
when `--router-mode kv_router` is active; they do not change round-robin routing or execution order
inside a selected engine.

### Multi-turn sessions

Use the same `session_id` for every turn in one session. Turn `n+1` waits for turn `n` to complete,
then applies `delay`, `delay_ms`, or the timestamp delta between consecutive rows.

```json
{"session_id":"session-a","timestamp":1000,"input_length":2048,"output_length":128,"hash_ids":[1,2,3,4]}
{"session_id":"session-a","delay_ms":50,"input_length":2560,"output_length":128,"hash_ids":[1,2,3,4,5]}
```

### Agentic Mooncake traces

Set `--trace-format agentic_mooncake` to model request-level dependencies. Each row requires a stable
`request_id` and can include:

| Field | Description |
|---|---|
| `wait_for` | Request IDs that must complete before this request starts |
| `branches` | Child request IDs spawned by this request |
| `prefix_reset` | Marks the first row in a session |
| `delay` | Additional delay after dependencies complete |
| `tool_wait_ms` | Simulated tool-execution delay |

Rows without `wait_for` use their timestamp as the start time. Rows with dependencies wait for all
listed requests and then apply `delay + tool_wait_ms`.

Agentic Mooncake is an input format for externally authored Mooncake-compatible traces. It is not an
intermediate representation for Dynamo request traces.

### Dynamo request traces

Set `--trace-format dynamo` to read one or more `dynamo.request.trace.v1` JSONL or JSONL.GZ shards.
DynoSim reads the original records directly and does not create an intermediate Mooncake file. It
derives and validates the trace block size across all shards.

Rows without `agent_context` use the standard request model. If every request contains
`agent_context`, DynoSim reconstructs the agent-aware model, including session dependencies and tool
waits. A replay cannot mix context-free and agent-aware request rows. For the complete capture schema,
see [Observe a Local Deployment](../../cli/operations/observability.mdx#capture-and-replay-requests).

`--trace-block-size` defines how many tokens each trace `hash_id` represents. It is independent from
the simulated engine `block_size`.

## Engine and router JSON

These flags take JSON strings. Engine settings such as `block_size`, `engine_type`, `dp_size`,
`speedup_ratio`, and `decode_speedup_ratio` belong here, not as top-level flags. Unspecified fields
fall back to `MockEngineArgs::default()` and `KvRouterConfig::default()`.

<ParamField path="--extra-engine-args" type="JSON string" default="null">
  Aggregated engine configuration. Accepts a partial JSON object.
</ParamField>

<ParamField path="--prefill-engine-args" type="JSON string" default="null">
  Prefill worker configuration for offline disaggregated runs. Must set `worker_type: "prefill"`.
</ParamField>

<ParamField path="--decode-engine-args" type="JSON string" default="null">
  Decode worker configuration for offline disaggregated runs. Must set `worker_type: "decode"`.
</ParamField>

<ParamField path="--router-config" type="JSON string" default="null">
  KV-router policy tuning, for example `{"router_queue_policy":"fcfs"}` or
  `{"router_prefill_load_model":"aic"}`. Accepts a partial JSON object.
</ParamField>

<ParamField path="--router-policy-config" type="path" default="null">
  Startup-only policy-family and cache-bucket queue YAML. Overrides `router_policy_config` inside
  `--router-config`. When omitted, DynoSim checks `DYN_ROUTER_POLICY_CONFIG`.
</ParamField>

<ParamField path="--model-name" type="string" default="null">
  Exact model profile to select from `--router-policy-config`. When omitted, the YAML root profile is
  used.
</ParamField>

Requests can set `policy_class` in Mooncake JSONL rows. A recognized policy family combines with the
router-observed uncached Input Sequence Length (ISL) bucket to select a physical queue. An exact
explicit class bypasses cache bucketing. Missing, unknown, and ordinary physical-class names use the
selected profile's `default_policy_family`. For the YAML schema and queue behavior, see
[Router Configuration](../../developer-guide/knowledge-base/modular-components/router/configuration-and-tuning.md#policy-class-queues).

### Experimental SGLang HiCache fields

Offline aggregated SGLang replay can model worker-local L2 plus one shared Mooncake-like L3. The
current experiment requires `router_mode=kv_router` and `block_size=256`; online and disaggregated
replay reject this configuration.

Configure HiCache inside `sglang` in `--extra-engine-args`. This four-worker example gives the
shared L3 `4 * 256 GiB` and uses the calibrated write-back host-IO rate:

```json
{
  "engine_type": "sglang",
  "block_size": 256,
  "num_gpu_blocks": 53108,
  "sglang": {
    "page_size": 256,
    "hicache": {
      "write_policy": "write_back",
      "l1_swa_capacity_tokens": 1359360,
      "l2_full_capacity_tokens": 54382592,
      "l2_swa_capacity_tokens": 5437440,
      "l3_capacity_gib": 1024,
      "io_tokens_per_second": 160000,
      "storage_layout": "dsv4_flash_tp4_attn_cp4_fp32"
    }
}
```

`write_through` serializes the complete physical bundle for each newly admitted logical page to L2
as soon as its device store becomes visible. `write_back` waits for device eviction and backs up the
components that are still resident at that boundary. In both modes, L3 receives only successful L2
backups. `io_tokens_per_second` is an effective calibrated L1↔L2 rate that includes PCIe transfer
and observed scheduler stalls, not raw link bandwidth. L3→L2 prefetch itself has zero modeled
transport cost, but every page actually loaded from L2 into L1 accrues H2D debt. Debt is serialized
per worker and added to its next scheduler pass. Set `l3_capacity_gib` to `0` for a local-L2-only
control while keeping the same WT/WB and host-IO accounting.

The `dsv4_flash_tp4_attn_cp4_fp32` layout accounts separately for C4, C4 indexer, C128, SWA, C4
state, and C4-indexer state. L3 enforces the configured GiB capacity in bytes and evicts all resident
objects for one logical 256-token page as a group. Shared-prefix presence is passed to the existing
KV-router scoring path through `shared_cache_hits`. When `--router-config` is omitted, HiCache replay
uses `shared_cache_multiplier=0.5`; an explicit router config remains authoritative. Ordinary SGLang
KV events do not identify the SWA/state boundary, so replay emits a private physical-metadata
sideband that the HiCache mirror consumes without inserting it into the ordinary KV indexer.

#### Current parity checkpoint

The research checkpoint below uses the 48,749-request Weka Claude Code trace
`9fa5480ca319a6f43700ba7826da387a5fc77e26390b61e2a09a87d3c39d29a5`, 28 workers, a 7,168 GiB
L3, ratio-4 L2, 256-token pages, and shared-cache multiplier `0.5`. It compares canonical DynoSim
replay with the source-span cache-emulator that established the experiment.

| Policy / implementation | Admission hit rate | p99 TTFT | Final L3 bytes |
|---|---:|---:|---:|
| write-back / cache-emulator | 54.6644% | 5.515 s | 3,955,933,490,688 |
| write-back / DynoSim | 63.7684% | 2.347 s | 5,701,908,976,320 |
| write-through / cache-emulator | 69.7441% | 3.285 s | 7,696,576,319,616 |
| write-through / DynoSim | 70.1130% | 3.078 s | 7,696,576,319,616 |

The write-through final state also matches exactly at 840,402 logical pages. This validates the
full-bundle byte geometry, hard capacity, and grouped replacement frontier; cumulative insertion and
eviction still differ because the two schedulers produce different page streams. The write-back gap
is intentionally not presented as parity: DynoSim uses SGLang's page-granular radix lifecycle while
the reference uses source-span nodes, and the remaining L3-byte delta is dominated by unresolved
SWA/state boundary retention (249,152 versus 46,008 trailing objects). Runtime event evidence is
required before treating either trailing-object count as conformance.

Both implementations derive the same ideal historical-L1 hit bound, 70.5070%. Their ideal p99 TTFT
values differ (1.208 s in DynoSim versus 1.359 s in the reference) because DynoSim uses its built-in
polynomial SGLang performance model while the reference uses a calibrated throughput curve plus a
fixed per-batch overhead. These results therefore validate cache contracts and relative behavior;
they do not establish hardware latency fidelity.

## Constraints

DynoSim validates these before running and fails immediately on any violation.

Shared constraints:

- `extra_engine_args.engine_type` must be `vllm`, `sglang`, or `trtllm`
- aggregated simulation requires the existing aggregated args path
- disaggregated simulation requires both `prefill_engine_args` and `decode_engine_args`
- disaggregated simulation requires `router_mode=kv_router`
- `dp_size` must be `1`
- disaggregated simulation requires matching `block_size` in `prefill_engine_args` and `decode_engine_args`

Additional offline constraints:

- offline `kv_router` requires `num_workers > 1`
- single-worker offline mode is a dedicated fast path for `vllm`, `sglang`, and `trtllm`;
  it supports flat request runs and workload-driven multi-turn runs
- offline disaggregated simulation is a separate two-stage runtime with prefill and decode worker pools
- SGLang HiCache requires aggregated offline `kv_router`, `block_size=256`, and page-aligned L1/L2
  capacities

Additional online constraints:

- the current live simulation path is also limited to aggregated workers

## Report schema

The report — and the equivalent Python APIs `dynamo.replay.run_trace_replay(...)` and
`dynamo.replay.run_synthetic_trace_replay(...)` — contains:

- request counts
- input and output token totals
- virtual duration and wall-clock runtime
- request and token throughput
- prefix cache reuse ratio
- TTFT, TTST, TPOT, ITL, and end-to-end latency summaries
- output-token-throughput-per-user summaries

SGLang aggregated reports additionally include `ideal_l1_zero_queue`. This trace-data reference
keeps every complete page from strictly earlier timestamp buckets in an unbounded L1, preserves the
production `input_tokens - 1` page clamp, and removes queue and transfer time. Its isolated TTFT uses
the configured SGLang performance model, chunked-prefill budget, speedup factors, and first decode
step. The nested `distance` object reports realized hit-rate and p99 TTFT gaps plus per-request TTFT
excess.

When HiCache is enabled, `sglang_hicache` records the physical DSV4 geometry, per-worker L2
capacities and final occupancy, calibrated IO rate, D2H/H2D token traffic, and byte-hard shared-L3
occupancy, insertion, rejection, and group-eviction counters. Its `route_*` fields are the
request-level cache potential immediately after the selected worker has been hydrated;
`admission_*` records what remains when the scheduler actually starts the request and is the reuse
value compared with `ideal_l1_zero_queue`. The difference exposes queue-time eviction or capacity
loss after routing. Prefer `admission_token_hit_rate` for realized HiCache experiments. The legacy
top-level `prefix_cache_reused_ratio` takes the maximum over all scheduler admissions, so a chunked
prefill can count chunks computed earlier by the same request; with HiCache enabled,
`first_admission_prefix_cache_reused_ratio` now matches the admission-level value.
